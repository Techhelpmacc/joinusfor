# Setup log — 2026-08-17

What was installed and verified, and the gotchas found along the way.

## Starting point

Both design skills turned out to be **already installed** in `~/.claude/skills/` from
7 August — so this was really an audit and update, not a fresh install.

## 1. frontend-design — no action needed

Checked the installed copy against the official source
(`anthropics/claude-code`, `plugins/frontend-design/skills/frontend-design/SKILL.md`).

After normalising line endings, both hashed **identically** (`1608ea77…`). The only
difference was CRLF vs LF. Already current — nothing to do.

> Note: fetching the GitHub URL returns a *summarised* version of the page, not the raw
> file. To compare properly, use the `raw.githubusercontent.com` URL or a git clone.

## 2. ui-ux-pro-max — updated

Installed copy was from **7 Aug: 44 files**. The repo had moved on, including a
13 Aug commit *"feat(search): overhaul relevance and curated design data"* (BM25
relevance, refreshed styles and component guidance).

Updated to **v2.13.0 — 70 files**. New additions included `catalog-summary.json`,
`data-provenance.json`, `google-font-licenses.json`, and an expanded `scripts/`
(now also `reasoning_contract.py`, `design_system.py`).

**Install method:** cloned the repo and copied `.claude/skills/ui-ux-pro-max/` straight
into `~/.claude/skills/`. Checked for symlinks first (the repo's own docs mention a
"zip contains a symbolic link" failure mode) — there were none. This avoided running
the project's npm/`npx` installer, i.e. no third-party install script executed.

**Gotcha found:** the backup was first written to
`~/.claude/skills/ui-ux-pro-max.backup-<timestamp>/` — and Claude Code immediately
loaded it as a **second, duplicate skill**. Moved it out. Never leave backups inside
the skills directory.

## 3. Python 3.13.15 — installed

The real blocker. `ui-ux-pro-max` drives everything through
`python scripts/search.py` (12 invocations across its SKILL.md), and **Python wasn't
installed** — so the search engine had never actually worked, including before the
update.

What looked like Python was the Windows **Microsoft Store stub** at
`WindowsApps\python.exe`, which only redirects to the Store. No `py` launcher either.

Installed with:

```bash
winget install --id Python.Python.3.13 --exact --silent --accept-package-agreements --accept-source-agreements
```

→ `C:\Users\Owner\AppData\Local\Programs\Python\Python313\python.exe`

**PATH check:** real Python landed at user-PATH position **1**, the Store stub at
**11** — so bare `python` resolves correctly. Confirmed by simulating a fresh shell:

```
python → C:\Users\Owner\AppData\Local\Programs\Python\Python313\python.exe
Python 3.13.15
```

## 4. End-to-end verification

Ran a real query, **exit code 0**:

```bash
python "<skill>/scripts/search.py" "local computer repair service macclesfield" --design-system
```

Returned a full design system — layout pattern ("Trust & Authority + Conversion" with
a hero → proof → solution → CTA section order), style, colour tokens as `--color-*`
variables, and accessibility annotations (contrast 4.5, keyboard, visible-focus,
reduced-motion).

A targeted UX query also returned correctly ranked WCAG guidance:

```bash
python "<skill>/scripts/search.py" "keyboard focus modal" --domain ux
```

## Lessons worth keeping

- Check whether a skill is **already installed** before installing — both were.
- A skill can look installed and still be **silently non-functional** if its runtime
  (here, Python) is missing.
- Verify a skill install by **running it**, not by checking files exist.
- On Windows, `python.exe` existing proves nothing — check it isn't the Store stub.
